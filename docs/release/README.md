# Release publishing

Push a version tag to run the release workflow. Accepted tags are `vX.Y.Z` and `vX.Y.Z-rcX`. Every release requires a nonempty `docs/release/vX.Y.Z-releasenote.md`; RC builds and the final release share that base-version file. Unsupported tags beginning with `v` fail validation.

Release notes may start with a document title such as `# ThreadLine 1.2.3`, followed by change sections such as `## Workspace`. Publishing automatically removes the leading level-one title from both the GitHub release body and updater notes, because their surrounding UI already identifies the version. Files without a leading title are also supported. Validation rejects empty or title-only notes; the source document keeps its title.

Keep `package.json`, the root entries in `package-lock.json`, `src-tauri/Cargo.toml`, and `src-tauri/tauri.conf.json` at the release version. RC tags use `v1.2.3-rc10`, while application versions use `1.2.3-rc.10`. The numeric prerelease component ensures that RC 10 is newer than RC 2 under SemVer. Update `src-tauri/Cargo.lock` with Cargo after changing the package version.

Before tagging, run:

```sh
node scripts/release.ts validate v0.1.0
npm run check
```

## Signing configuration

Configure these repository settings before publishing:

- Variable `THREADLINE_UPDATER_PUBLIC_KEY`: the public verification key generated by the Tauri signer.
- Secret `TAURI_SIGNING_PRIVATE_KEY`: the corresponding private signing key contents.
- Secret `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`: the private key password, if used.

Keep an independent backup of the private key. Changing it without a migration breaks the upgrade path for installed copies. Never commit a private key. Use the [Tauri updater signing instructions](https://v2.tauri.app/plugin/updater/#signing-updates).

The build job fails when the public or private key is absent. It injects public updater configuration through an ignored `.release-config.json`; normal source/debug builds stay runnable and show that updates are unavailable. Application signing and notarization are separate from updater signing. For macOS, the workflow forwards the `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_PASSWORD`, and `APPLE_TEAM_ID` secrets when configured. Windows Authenticode signing requires a separately configured signing provider; updater signatures do not replace it.

## Pipeline and channels

The workflow validates the tag, versions, and release note before building. Each platform runs the complete project checks, then builds signed updater artifacts for Apple Silicon macOS, Intel macOS, and Windows x64. Publishing requires all three artifact sets, their signatures, and installer files. A failed platform build never publishes a partially populated channel.

Versioned releases contain immutable-version download URLs and the release note content. Stable tags produce normal releases; RC tags produce prereleases. The separate `update-channel` prerelease holds replaceable `stable.json` and `preview.json` manifests. It is infrastructure, not an application version, and is never marked as the latest stable release. Release builds embed their channel endpoint. Channel publication refuses version downgrades. A stable release also advances the preview channel when that channel does not already contain a newer version, allowing RC installations to graduate to the final version.

The application checks automatically after startup and every six hours when enabled, or manually in Settings → About and Updates. Downloads display progress. Installation is explicitly requested with “Install and restart”; the application flushes local workspace changes first. A failed save, check, download, or restart can be retried without silently claiming success. Windows may exit into its installer; macOS relaunches after installation.

## Release acceptance

For the first live release, configure signing, build a versioned installer, and verify an upgrade from that installation to a later signed version on each supported platform. Also exercise offline checks, interrupted downloads, invalid signatures, unavailable architectures, and local-save failure. Unit tests cover the application state transitions and release policy; they do not substitute for an actual operating-system installer test.
